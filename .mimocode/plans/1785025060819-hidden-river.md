# Suitora — Implementation Plan for Future Features

Based on `docs/future_features_implementation.md` and full codebase exploration.

---

## Current State Assessment

**What's actually working (better than the alignment report suggests):**

- **Schema** (`drizzle/schema.ts`): Already has `status`, `updatedAt`, `productId`, `compatibilityMetadata`, `height/weight` fields. Schema is in good shape.
- **API Routes**: Full CRUD for analyses, favorites, dashboard stats, profile, self-image — all wired to the database.
- **UI Pages**: Dashboard, Upload, Analysis, Results, History, Favorites — all fetch from real API routes, not mock constants.
- **Size Prediction** (`lib/ai/size-prediction.ts`): This is actually real logic using size charts — not mock.

**What's genuinely mock (needs real implementation):**

| Module | File | Current State |
|--------|------|---------------|
| Image upload | `lib/ai/upload.ts` | Converts to base64 data URLs (no Cloudinary) |
| Product extraction | `lib/ai/product-extraction.ts` | Returns `/placeholder.svg` + random titles |
| Body estimation | `lib/ai/body-estimation.ts` | Random scores based on URL string hash |
| Virtual try-on | `lib/ai/tryon.ts` | Returns the original clothing image |
| Analysis scoring | `app/api/analysis/route.ts` | Uses `randomScore()` for all scores |

**Schema gaps vs `docs/data_schema.md`:**

- `favorites` table lacks `UNIQUE(user_id, analysis_id)` constraint
- `favorites` table lacks `product_id` column
- Column naming differs (`userImage` vs `user_image_url`) — cosmetic, not blocking

## Implementation Order

### Phase 0: Schema Hardening (Quick, unblocks everything)

**Goal:** Fix the two schema gaps before building on top of them.

1. Add `UNIQUE` constraint on `favorites(user_id, analysis_id)`
2. Add `product_id` to `favorites` table (optional FK)
3. Generate and apply migration

**Files:**
- `drizzle/schema.ts` — add unique constraint, add product_id
- `drizzle/migrations/` — new migration file

**Verification:** Run `npx drizzle-kit generate` and `npx drizzle-kit push` (or `migrate`). Confirm favorites rejects duplicates.

---

### Phase 1: Cloudinary Image Hosting

**Goal:** Replace base64 data URLs with proper CDN-hosted images.

**Why first:** Every subsequent feature (AI analysis, product extraction, try-on) needs reliable image URLs. Base64 blobs bloat the DB and don't work with vision APIs.

**Steps:**
1. Create `lib/storage/cloudinary.ts` — upload, optimize, generate CDN URL
2. Update `lib/ai/upload.ts` to call Cloudinary instead of FileReader
3. Store returned URLs in analyses table (`userImage` / `productImage`)
4. Optionally track in `uploads` table
5. Add retention policy config (90-day default)

**Files to create/modify:**
- `lib/storage/cloudinary.ts` (new)
- `lib/ai/upload.ts` — replace base64 logic
- `app/(dashboard)/upload/page.tsx` — may need to handle async upload differently

**Dependencies:** `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` env vars

**Verification:** Upload a photo, confirm it appears as a Cloudinary URL (not `data:image/...`), and persists after page reload.

### Phase 2: Real AI Vision Integration

**Goal:** Replace all mock AI with real vision model calls.

**Steps:**
1. Create `lib/ai/vision.ts` with abstract interface:
   ```ts
   analyzeFashion(userImageUrl, clothingImageUrl) → AnalysisResult
   ```
2. Implement OpenAI Vision adapter (primary) and Gemini Vision adapter (fallback)
3. Replace `randomScore()` calls in `app/api/analysis/route.ts` with real model output
4. Replace `lib/ai/body-estimation.ts` with real vision-based estimation
5. Replace `lib/ai/tryon.ts` — either real try-on API or graceful fallback
6. Map model output to canonical fields: scores, bodyShape, skinTone, faceShape, styleType, recommendations, colorAnalysis, compatibilityMetadata
7. Add retry logic, rate limit handling, and mock fallback for degraded mode

**Files to create/modify:**
- `lib/ai/vision.ts` (new — provider abstraction)
- `lib/ai/providers/openai-vision.ts` (new)
- `lib/ai/providers/gemini-vision.ts` (new, optional)
- `lib/ai/body-estimation.ts` — replace mock with real vision call
- `lib/ai/tryon.ts` — replace mock or mark as optional
- `app/api/analysis/route.ts` — wire real analysis pipeline

**Dependencies:** `OPENAI_API_KEY` (or Gemini credentials), working Cloudinary URLs

**Verification:** Run a real analysis end-to-end. Confirm scores are non-random, body traits are plausible, and recommendations are context-aware. Confirm status progression (pending → analyzing → completed) works.

### Phase 3: Product URL Extraction (Real)

**Goal:** Replace the placeholder scraper with real e-commerce image extraction.

**Steps:**
1. Replace `lib/ai/product-extraction.ts` with real scraper
2. Options: use a headless browser service (Puppeteer/Playwright), or a commercial API (e.g., Diffbot, ScrapingBee)
3. Extract: primary product image, title, brand, price
4. Store in `products` table
5. Add cache key: `product:url:{encodedUrl}:id` (TTL 24h)
6. Handle edge cases: blocked sites, multi-image pages, anti-bot

**Files to modify:**
- `lib/ai/product-extraction.ts` — replace mock with real scraper
- `app/api/analysis/route.ts` — already calls `extractProductFromUrl`, should just work

**Verification:** Paste a real product URL from Zara/H&M. Confirm image, title, brand, and price are extracted and stored in the products table.
